# 計測中バナーの時刻を全幅まで拡大する 設計書

## 背景

`2026-08-12-banner-large-time-design.md` で時刻を 30px から 44px に拡大したが、
iOS 標準のストップウォッチと並べるとまだ半分以下だった。計測中に部屋の反対側から
見えることがバナーの価値なので、行の幅いっぱいまで拡大する。

## 方針

フォントサイズを固定値ではなく**行の内容幅に比例させ**、時刻の**桁数を固定する**。

### 幅の基準に Container Query 単位（`cqw`）を使う

`.rb-row` に `container-type: inline-size` を置き、時刻を `min(23cqw, 104px)` にする。

`vw` は使えない。`body` に `max-width: 640px` があるため、画面幅とバナー幅は
広い画面で一致しなくなり、`vw` 基準だと文字が行からはみ出す。`cqw` はバナー自身の
内容幅を基準にするので、狭い端末でも広い画面でも同じ「全幅に収まる」比率が成立する。

上限 104px は、大画面で文字だけが無制限に育つのを止めるため。

### 時刻を常に `HH:MM:SS` にする

`fmtElapsed` は `MM:SS`（1時間以上は `H:MM:SS`）を返していた。全幅まで拡大すると、
**桁数が変わった瞬間にフォントサイズと字の位置が跳ぶ**。1時間ちょうどと10時間ちょうどの
2回、表示が明らかに崩れる。

時を省かず2桁に揃えれば桁数は常に8で固定され、99時間まで寸法が動かない。iOS の
ストップウォッチが `00:03.26` と2桁固定なのも同じ理由と思われる。

`fmtElapsed` の利用箇所はバナーのみ（記録一覧は別の整形を使う）なので、影響範囲は
計測中バナーに閉じている。

### 23cqw の根拠（実測）

ブラウザで `.rb-time` の描画幅を Range API で実測し、行の内容幅と比較した。

| 端末幅 | 内容幅 | フォント | `00:00:00` の余白 | `99:59:59` の余白 |
|--------|--------|----------|------------------|------------------|
| 320px  | 252px  | 58.0px   | 9.5px            | 9.5px            |
| 375px  | 307px  | 70.6px   | 13.2px           | 13.2px           |
| 393px  | 325px  | 74.8px   | 14.5px           | 14.5px           |
| 430px  | 362px  | 83.3px   | 16.9px           | 16.9px           |
| 640px超 | 572px | 104.0px（上限） | 141px    | 141px            |

桁数によらず余白が同一なのは `tabular-nums` が効いている証拠である。

当初は 7 文字（`H:MM:SS`）を前提に `28cqw` としたが、実測で**時が2桁になると
375px 幅で 49px はみ出す**ことが判明した。8 文字が収まる上限は 24.1cqw で、
安全マージンを取って 23cqw とした。

### バナーの高さに上限を設ける

利用者の選択により、同時計測が何件でも時刻は縮めない（一覧性より視認性を優先）。
その結果、行が積み上がるとバナーが画面高を超え、`position: fixed; bottom` のため
**上端の行が画面外に出て触れなくなる**。

`max-height: calc(100dvh - env(safe-area-inset-top) - 24px)` と `overflow-y: auto`
で上限を切る。5件同時計測（内容 972px）で高さ 839px に制限され、上端は画面内に
留まり、スクロールで全行に到達できることを確認した。

なお**想定する同時計測は最大2件**であり、その範囲ではバナーは 400px 程度に収まって
上限に達しない。この `max-height` は、想定を超えて行が積み上がったときに上端の行が
画面外に出て操作できなくなる事故だけを防ぐ保険である。

## 却下した案

1. **件数でサイズを段階的に縮める**（1件=最大、2件=中、3件以上=現状）: 一覧性は
   保てるが、利用者が「常に大きく」を選択した。件数×桁数で組み合わせも増える。
2. **桁数でサイズを変える**（`MM:SS` のときだけ最大）: 1時間未満はより大きくできるが、
   1時間ちょうどで見た目が跳ぶ。桁数固定の方針と相反する。
3. **タップで全画面タイマー**: 前回の設計書で却下済み。常時見えていることが
   バナーの価値であり、見るためにワンタップ必要になる。

## 実装

- `index.html`: `.rb-row` に `container-type: inline-size`、`.rb-time` を
  `min(23cqw, 104px)` / `line-height: 1.02` / `font-weight: 200` / `text-align: center`、
  `#runningBanner` に `max-height` と `overflow-y: auto`
- `app.ts`: `fmtElapsed` を常に `HH:MM:SS` を返すよう変更、行テンプレートの初期表示も
  `00:00:00` に揃える

`font-weight` を 300 から 200 に下げたのは、この寸法では 300 が太く見えるため。
`line-height` は 1.1 のままだと 104px の行が 114px を占め、バナーが不要に伸びる。

最下部カードが隠れない余白は `renderBanner()` が `offsetHeight` を実測するため
自動で追従する。想定する最大2件ではカード一覧も見えたままだが、5件に達すると余白が
画面高を超えて一覧は事実上見えなくなる。そこまで積み上げる運用になったときは
却下案 1（件数でサイズを段階的に縮める）への切り替えで対処できる。

## リリース

- ユーザーに見える変更なので `package.json` の `version` を 1.3.5 → 1.3.6 に上げる
- `index.html` と `app.js` は network-first で配信されるため `sw.js` の `CACHE`
  バンプは不要

## テスト

`mise exec -- npm run build` が通ることを確認した上で、ローカルサーバーで確認した。

1. 単独計測: 320〜640px 超の各幅で時刻が全幅に収まり、はみ出さない（上表）
2. 桁数固定: `00:00:00` と `99:59:59` の描画幅が一致し、寸法が動かない
3. 5件同時計測: バナーが 839px で頭打ちになり上端が画面内に留まる、
   スクロールで全行に到達できる
4. 一時停止の暗転: 一時停止行のみ `rgba(0,0,0,.22)`、計測中の行は透明のまま
5. 「破棄？」の armed 表示: 赤 `rgb(220,38,38)` になり、ボタン行は行幅に収まる
